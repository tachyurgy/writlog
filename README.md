# Writlog

A case engine for commercial collections litigation: every matter is a projection of an append-only event log, deadlines are computed from New York rules and rolled past weekends and court holidays, and documents are generated by background jobs that cannot produce the same document twice.

Live: https://writlog.levelbrook.com (fictional data, reseeded on deploy)

Rails 8.1, PostgreSQL, ActiveJob on Solid Queue, Active Storage, and one React 19 island loaded through importmap from esm.sh (no Node in the build or runtime image).

## What it does

| Area | Where | What to look at |
|---|---|---|
| Workflow state machine | `app/models/workflow.rb` | `TRANSITIONS` table, pure `fold`, `replay`, locked `append!` |
| Append-only log | `db/migrate/*_create_domain.rb` | `(matter_id, seq)` unique index, `BEFORE UPDATE OR DELETE` trigger |
| Deadlines | `app/models/court_calendar.rb`, `app/models/deadline_rules.rb` | NY GCL 24 holidays, GCL 25-a roll-forward, CPLR 320(a), 308, 3215(c), 5222(b) |
| Document generation | `app/services/document_request.rb`, `app/jobs/generate_document_job.rb` | inputs digest, unique index, row-locked idempotent job |
| Rendering | `app/services/document_renderer.rb` | HTML preview (escaped) and PDF via Prawn |
| Communications | `app/models/communication.rb` | every letter, call, email or filing also lands on the event log |
| React island | `app/javascript/islands/document_composer.js` | merge-field inspector, live preview, "generate twice at once" race button |

## The workflow

```
intake -> demand_sent -> suit_filed -> served -> answered ----------> judgment_entered -> enforcement
                                          \-> in_default ---------/        |                 |
          (settlement_reached from any active state) -> settled -> satisfaction_filed -> satisfied
          (matter_closed from any active state) -> closed
```

`Workflow.fold(projection, kind, effective_on, payload)` is a pure function. It validates the event (legal from the current state, required payload present, not back-dated, a default only after the answer deadline has passed) and returns the next projection: state, balance fields, service method, answer deadline, default-judgment clock, restraint expiry, and the next deadline with its label.

`Workflow.append!` is the only write path. Inside one transaction it takes `SELECT ... FOR UPDATE` on the matter row, folds the new event into the current projection, inserts the event with `seq = events_count + 1`, and writes the projection back with `update_columns`. A rejected event raises before anything is written.

Because the same `fold` is used for replay, the stored projection is checkable at any time: `Workflow.replay(matter.matter_events) == matter.projection`. The matter page runs that comparison on every load and shows the result.

Audit events (`document_generated`, `communication_logged`) are recorded on the log but never move the state or the matter's "as of" date. That matters for idempotency: recording that a document was generated must not change the inputs of that same document.

The log is append-only in the database, not just in Ruby. A plpgsql trigger raises on `UPDATE` or `DELETE` of `matter_events`, so `update_all` and raw SQL are rejected too. Because of that trigger the schema is kept as `db/structure.sql`, and the container runs `db:migrate` on boot (not a schema load) so the trigger comes from the same migration everywhere.

## Deadlines

- Personal delivery (CPLR 308(1)): answer due 20 days after service.
- Deliver and mail, affix and mail (CPLR 308(2), 308(4)): service is complete 10 days after proof of service is filed; answer due 30 days after that.
- Corporation served through the Secretary of State (BCL 306): 30 days.
- A noted default starts the one-year window of CPLR 3215(c).
- A restraining notice is effective for one year after service (CPLR 5222(b)).
- Every computed date is rolled forward past Saturdays, Sundays and New York public holidays (General Construction Law 24 and 25-a, with Sunday holidays observed on Monday). Each `Deadline` keeps the raw date, the rolled date, the rule text and the reason for every skipped day, and the UI shows all of it.

Example from the seed data: served by deliver-and-mail on 2026-08-28, proof filed 2026-09-01, so service completes 2026-09-11 and the raw answer date is Sunday 2026-10-11. Monday 2026-10-12 is Columbus Day, so the answer is due Tuesday 2026-10-13.

The rules are illustrative, not legal advice. Court-specific closures would be data rows, not code.

## Documents, exactly once

1. `DocumentRequest.call(matter, template)` resolves the template's `{{merge_fields}}` against the matter. Missing values block generation (the composer shows which ones and disables the button).
2. It hashes `(template id, template version, sorted merged values)` into `inputs_digest`. The document date field (`as_of`) is the date of the latest workflow event, not "today", so the same matter state always yields the same digest.
3. The row is keyed by a unique index on `(matter_id, document_template_id, inputs_digest)`. The creator takes the matter row lock only to keep the per-template version counter gap-free; if any writer ever bypasses that lock, the index still decides and the loser gets `RecordNotUnique`, which is rescued into "return the existing row".
4. Only the caller that actually inserted the row enqueues `GenerateDocumentJob`.
5. The job `with_lock`s the document row, returns immediately if it is already `ready`, renders HTML and a PDF (Prawn, pure Ruby, no headless browser in the image), uploads the PDF to Active Storage synchronously, marks the row ready and appends one `document_generated` event. A unique partial index (`index_matter_events_one_per_document`) makes a second log entry for the same document impossible.

When the inputs change (a payment lowers the balance), the digest changes and a new version is produced. Old versions stay, each pointing at the exact template version it was merged from. Templates are immutable once used; editing one means publishing version N+1.

### Background jobs: Solid Queue here, Sidekiq-ready

Jobs use only the ActiveJob API (`perform_later`, `retry_on`, `discard_on`, `queue_as`). They do not use Solid Queue-only features such as `limits_concurrency`; mutual exclusion comes from Postgres row locks and unique indexes, which behave the same under any backend. Running on Sidekiq is a one-line change in `config/application.rb` (`config.active_job.queue_adapter = :sidekiq`) plus a Redis URL.

In this deployment Solid Queue runs inside Puma in `async` mode (threads, not forked processes; see `config/puma.rb`) and its tables live in the primary database, so the whole app is one small container.

## Tests

```
bin/rails db:create db:migrate
bin/rails test
```

31 tests, about 7,000 assertions (Minitest). The ones that carry the correctness claims:

- `test/models/workflow_test.rb`: a property test that runs 40 random walks through the state machine (mostly legal events, about 20% arbitrary ones to hit the guards) and asserts after each walk that the stored projection equals a fresh replay, `seq` is exactly `1..n`, and a rejected event left no trace. Also: the trigger rejects `update_all` and `delete_all`.
- `test/models/court_calendar_test.rb`: a property test over 2,000 random dates from 2018 to 2035 asserting the rolled date is the earliest business day on or after the raw date.
- `test/models/concurrency_test.rb` (real threads, real connections, transactional tests off):
  - 8 threads request the same document at once, three rounds: exactly one row, exactly one caller sees `created`, one job enqueued per round.
  - The unique index alone rejects a duplicate insert, with no lock involved.
  - 8 threads run the same `GenerateDocumentJob` at once: one PDF attachment, one `document_generated` event, `attempts == 1`.
  - 8 threads append payments to one matter at once: `seq` stays gap-free and the balance is exact.
- `test/integration/flows_test.rb`: the JSON API returns 201 then 200 with the same document id, and the rendered PDF is served through Active Storage.

## Running locally

Requires Ruby 3.3.7 and PostgreSQL. With a PostgreSQL 17 server, put the 17 client tools first on `PATH` so `db:migrate` can dump `structure.sql`.

```
bundle install
bin/rails db:create db:migrate db:seed
bin/rails server
```

## Deployment

One container on a small Hetzner VM behind kamal-proxy (TLS via Let's Encrypt), capped at 300 MB, sharing a PostgreSQL 17 container with its own database. Active Storage uses the Disk service on a named volume; `config/storage.yml` is the only change needed to move PDFs to S3.

```
rsync -a --exclude .git --exclude log --exclude tmp --exclude storage ./ root@HOST:/root/writlog/
ssh root@HOST 'cd /root/writlog && docker build -t writlog:latest . && \
  docker run -d --name writlog --restart unless-stopped --network kamal --memory 300m \
    --env-file /root/writlog/.env.prod -v writlog_storage:/rails/storage writlog:latest && \
  docker exec kamal-proxy kamal-proxy deploy writlog --target writlog:3000 --host writlog.example.com --tls'
```

`.env.prod` holds `DATABASE_URL`, `SECRET_KEY_BASE`, `RAILS_ENV=production`, `RAILS_LOG_TO_STDOUT=1`, `RAILS_MAX_THREADS=3`.
